# AEGIS

Privacy-focused desktop browser built with Electron. Zero tracking, zero cache persistence by default, per-user workspaces, and a fully local profile.

## Features

- **Per-user accounts** — local-only registration (SQLite + salted password hashing), guest mode, optional profile photo.
- **Workspaces** — each user gets isolated workspaces with their own tabs, restored automatically on login. Split-screen mode for two workspaces side by side.
- **Tab session persistence** — tabs auto-save every 30 seconds and on quit, so a crash never costs you your session.
- **Downloads manager** — per-workspace download list, progress events, open-in-folder, delete, plus a **workspace-wide download shelf**: a strip above the status bar listing every download of the current workspace with its **percentage, progress bar, status (Pending / Downloading / Completed / Failed) and file name** — it survives tab switches, navigation and new tabs, keeps several downloads visible at once, and shows the final state for a few seconds even if you are somewhere else in the browser.
- **Browsing history & bookmarks** — per-workspace history with visit durations, bookmarks, per-workspace notes.
- **Activity dashboard** — daily / weekly / all-time analytics, opt-out toggle.
- **Idle auto-close** — configurable timer that locks/closes the session after inactivity.
- **Login self-destruct** *(new in v1.1)* — enter the wrong password **3 times in a row** and AEGIS erases every trace of local data: accounts, history, bookmarks, downloads, cookies/localStorage (workspace partitions) **and the whole Chromium profile** — site permission grants, Local State, DIPS bounce-tracking records, ad interest groups. The failed-attempt counter is stored on disk in the main process, so restarting the app cannot reset it; only a successful login does. Profile files Windows refuses to delete while Chromium still holds them are queued in `pending-wipe.json` and removed at the next launch, before anything is opened. The login screen keeps showing what happened — even after a restart — until a new account is created. Afterwards it is fully usable again with a fresh, empty database.
- **Default browser integration** *(new in v1.1)* — registers a proper ProgId + `RegisteredApplications` capabilities entry so Windows Settings lists AEGIS; deep-links straight to its default-apps page. Links clicked anywhere in Windows open in a new AEGIS tab (cold start via `process.argv`, running instance via `second-instance`).
- **Network speed controls** *(new in v1.1)* — multi-connection parallel downloads, plus an opt-in **Secure DNS (DNS-over-HTTPS)** toggle in Settings.
- **Test Internet speed** — a button in the Connection panel (toolbar globe icon) measures **latency, jitter, download and upload** in one press (~10–25 s). It streams dummy test payloads from public keyless endpoints in the main process (Cloudflare, with OVH/Hetzner fallbacks), streams live progress to the panel, then renders a **0–100 score** with a rating (Excellent → Very poor), a plain-language verdict, per-use verdicts (4K streaming, video calls, gaming, large downloads, …) and actionable tips. Nothing about you or your browsing is sent — only the test files move — and results are never written to disk.
- **YouTube video download** *(new in v1.1)* — while a YouTube page is open, a **Download** button appears in the toolbar. Pressing it reads the video's available qualities (capped at 1080p, **1080p preselected as the default**), shows sizes, and downloads the chosen quality as a single **MP4** — **you choose the destination folder** from the menu (a folder row shows where files land; **Change** opens the system folder picker and the choice is remembered across restarts, defaulting to the Downloads folder) — or set it any time from the **AEGIS menu → Youtube Download parameters**, which opens a small window where you **Choose folder…** and press **Save** — with video and audio streams merged automatically. The quality menu **floats above the page content** in its own overlay layer (so the page can never cover it) and **flies back to its toolbar anchor ~5 s after opening**, pausing while you point at it; a running download keeps it up so progress and Cancel stay reachable. Progress is shown live on the button, in the menu and in the workspace-wide download shelf (and the Downloads panel), with cancel support. The extraction runs in the main process through **yt-dlp + ffmpeg**, which AEGIS downloads once into `%LOCALAPPDATA%\AEGIS\tools` on first use (resumable, with retries). No account, no cookies — only the video you asked for is fetched.
- **Download Full Playlist** *(new)* — on a complete **YouTube playlist page** (`youtube.com/playlist?list=…`) the toolbar shows a **Download Full Playlist** button; it is **mutually exclusive with the single-video Download button** — ordinary video pages (including `watch?v=…&list=…`), `/playlist` without a list id and unrelated sites never show it. Pressing it opens a dedicated, frameless **playlist window** that streams the playlist's videos from yt-dlp as they arrive: thumbnail, title, duration and an availability badge per row, **everything preselected**, with **Select all / Deselect all**, a filter, a live selected count and a quality choice (1080p default; 720/480/360p). **Download Selected Videos** queues the selection and the queue downloads the videos **strictly one at a time — the next video starts only after the current one has completely finished or failed** (a single-worker state machine in `playlist-queue.js`, so two playlist videos can never download in parallel), in playlist order, through the **same yt-dlp engine** as the single-video button — progress, the download shelf, the Downloads panel and the database mirror all keep working unchanged. The queue view shows per-video status (Waiting / Downloading / Completed / Failed / Skipped), percentage, speed, size and errors, plus overall completed / waiting / failed counts and the current video, with **Pause** (the current video finishes first, nothing new starts), **Resume**, **Skip current**, **Retry failed**, **Remove** on videos that have not started yet, and **Cancel queue** — a failed video never blocks the rest, duplicate entries are dropped, and **closing the window never stops the queue**: reopening it shows the live state again.
- **Geolocation always refused** *(new in v1.1)* — a site asking for your location is refused **automatically, silently and permanently**: the permission is denied at the check level (so `navigator.permissions` reports `denied` and nothing can quietly opt into the OS location service) and again at the request level, *before* the Allow/Deny dialog is built — so **no popup is ever shown for geolocation**, not even for a site you once allowed. Every other permission (camera, microphone, notifications, …) keeps its normal Allow/Deny dialog.
- **Two permissions approved silently** *(new)* — `persistent-storage` (OPFS / `navigator.storage.persist()`) and `clipboard-sanitized-write` (the sanitized async clipboard **write** half — `navigator.clipboard.writeText()` from a real user gesture) are granted **automatically at the session level**: one central handler in `setupSession` whitelists exactly these two strings at both the check and request level, so **no Allow/Deny dialog is ever shown for them** — in the default session, in every workspace tab, in a freshly opened tab, in a **brand-new workspace**, on a **real third-party HTTPS website** and after a restart. Every other permission keeps its existing policy: camera, microphone, notifications, clipboard **read** and screen sharing still raise the normal Allow/Deny dialog, and geolocation is still silently refused (above). No per-tab handlers and no UI workarounds — the list lives in one deliberately minimal place (`AUTO_APPROVED_PERMISSIONS` in `main.js`).
- **Default download folder** *(new)* — **AEGIS menu → AEGIS Parameters** now has a **Download folder** card: pick where **all** downloads reside. It is the destination used by every download, and it is also **the default location of YouTube downloads — unless the user chooses another one** in **AEGIS menu → Youtube Download parameters** (which can also *Use the default downloads folder* to follow AEGIS Parameters again). Both windows share the same native folder picker, show the current path, and only persist on **Save**; `AEGIS_DOWNLOADS_DIR` still pins the folder for automated runs.
- **Ghost Mode badge in Anonymous mode only** *(new)* — the **Ghost Mode** badge on the top bar is shown **only when browsing in Anonymous (guest) mode** ("Continue without account"): guest accounts are flagged in SQLite (`users.is_guest`) and `get-user` reports `guest`, so registered accounts never see the badge.
- **Workspace email persisted + background detection** *(new)* — the Google account email shown on a workspace card is **saved in SQL** (`workspaces.google_email`) and displayed right away on every visit. While AEGIS runs, a **background watcher** re-reads the open Gmail tabs (every 90 s, plus a debounced check whenever Google auth cookies change in a workspace partition) and detects **another — or a newly opened — email on the workspace**: the new address is stored and pushed live to the workspace screen, which updates the card in place.
- **Menu bar in fullscreen** *(new)* — AEGIS starts fullscreen, and the **AEGIS and Workspaces menus stay visible in fullscreen mode**: entering fullscreen Chromium finishes hiding the menu bar *during* the transition (after the `enter-full-screen` event fires), so the menu is rebuilt and re-forced visible again once the transition has settled (150 ms and 500 ms after the event) as well as after every application-menu rebuild (login, workspace switch, window restore). Creating, renaming or deleting a workspace also rebuilds a currently-shown menu so its Workspaces list stays in sync — you can switch workspaces straight from the menu without leaving fullscreen.
- **Clock in the top-right toolbar in fullscreen** *(new)* — while AEGIS is in **fullscreen mode**, the **top-right toolbar shows a live clock** ( HH:MM:SS, local time, ticking every second, next to the fullscreen button). It is rendered **only** when the window is fullscreen (`body.fs` set from the `fs-change` IPC): leaving fullscreen hides it and stops its timer, and it never appears in windowed mode. The timer starts and stops with the fullscreen state, so nothing ticks while the clock is hidden. It is also suppressed on very narrow windows (≤980 px) so it can never push the toolbar buttons off-screen, and it disappears with the rest of the chrome when a page itself goes HTML-fullscreen.
- **Delete workspace asks for confirmation** *(new)* — pressing **Delete** on a workspace card no longer deletes anything: it opens a **confirmation message** naming the workspace (tabs, history, bookmarks and notes will be removed — *This cannot be undone*), and only **Delete Workspace** in that dialog actually deletes; **Cancel** or **Escape** backs out safely.
- **Ghost Workspace** *(new)* — a standing first card on the workspace screen that opens a workspace living **entirely in RAM**: its session partition is created **without the `persist:` prefix**, so Chromium never writes cookies, cache or localStorage to disk, and no row is ever inserted for it in SQLite (no tabs, history, bookmarks, notes, downloads or analytics — bookmarking and notes are refused while it is active, and it never becomes the remembered "active workspace"). Every visit gets a **brand-new partition name**, so nothing from a previous visit can resurface; leaving the workspace (or quitting) destroys its views and discards the whole session. The card shows an **"In-memory only"** pill, says *Nothing is written to disk*, and has no rename/delete buttons — it is simply discarded, never deleted. It is excluded from split view.
- **Duress password (panic decoy)** *(new)* — a **second password** (Settings → Profile) that opens a **separate, believable-but-empty account**: a normal-looking Default workspace and nothing else, while your real account, workspaces, history and files stay **completely untouched on disk** — nothing is deleted, and the login screen behaves identically. The typed pseudonym is what the UI shows (never an internal key), every credential prompt inside the decoy (change password, duress setup) answers with the ordinary *"Current password is incorrect."*, and the History/Notes gates unlock with the duress password. Setting it requires a password different from your main one; removing it is one button. Login timing cannot betray it: authentication always burns **exactly two PBKDF2 derivations** (real + duress, or a discarded filler), so a duress login costs the same as a real one.
- **Aegis Shield** *(new)* — three privacy protections that all run **before anything leaves the machine**, each with its own switch in **Settings → Aegis Shield**:
  - **Ad & tracker blocker** — a local **domain trie** built from the bundled `shield-list.txt` — a **real, unmodified EasyList + EasyPrivacy dump** (licence headers kept) of **99,264 loaded rules** (`||domain^`, `||domain/path^`, bare domains, `@@` exceptions and the `$third-party` / resource-type / `$domain=` modifiers; the current bundle also rejects **34,511** rules it cannot honour) — is consulted from `session.webRequest.onBeforeRequest`, so a matching request is **cancelled before DNS runs and before the HTTP socket opens** — no extension, no external list to download, and it cuts load time and bandwidth. Your own rules live in `shield-custom.txt` in the profile folder (same syntax, one per line) and are loaded on the next launch. The parser **never guesses**: a rule with an unknown modifier (or cosmetic/regex/wildcard syntax) is **rejected outright and counted**, never loaded in a half-understood form that could block the wrong thing — a partially applied rule is worse than no rule.
  - **Canvas / WebGL fingerprint randomizer** — a sandboxed `fp-preload.js` attached to every content view flips **1–2 of the least significant bits of ~1/16 of the pixels** in `getImageData`, `toDataURL`, `toBlob`, `OffscreenCanvas.convertToBlob` and WebGL `readPixels`. Alpha is never touched, canvases above 2 MP (exports/snapshots) are left alone, and `toDataURL`/`toBlob` work on a scratch copy so **the page's own canvas is never mutated** — only the encoded bytes a tracker hashes differ. The noise is derived from a **seed that changes on every AEGIS launch** combined with `location.origin`, so a fingerprint can be linked neither across sessions nor across sites, while staying **deterministic within one origin**: repeated reads return identical bytes, so equality checks, CAPTCHAs and anti-fraud "did it change?" tests keep working. WebGL *capability* values (`MAX_TEXTURE_SIZE` …) are **never** faked — only the unmasked vendor/renderer strings are farbled — so games and 3D pages render exactly as before.
  - **Tracking-parameter strip** — `utm_*`, `fbclid`, `gclid`, `msclkid`, `igshid`, `li_fat_id`, `mc_eid` … are removed from every **GET navigation** (main frame *and* subframes) by redirecting to the cleaned URL, so the tracker never sees the tag and the address bar / history entry is already clean. Functional parameters (`ref`, `source`, `id`, …) are deliberately kept, and a redirect-loop guard stops a server that keeps re-adding tags from bouncing you forever.
  - Live counters (**rules loaded**, **requests blocked**, **URLs stripped**, top blocked hosts) are shown on the same Settings card and persisted to `shield-prefs.json` in the profile folder. All three toggles apply immediately — no restart.
- **Continue with Google (and every other SSO)** *(new)* — AEGIS intercepts every `window.open()`, and turning an identity-provider popup into an ordinary tab would drop `window.opener`: the callback page could never `postMessage()` the result back, so the site never learns the login finished and re-triggers itself (the infinite *"Continue with Google"* loop). Recognised logins (Google, Apple, Microsoft, OpenAI, Discord, Yahoo, Auth0, Okta, Amazon Cognito, plus any `/oauth…`/`/authorize` endpoint) now open a **linked popup** instead: a real child window that keeps `window.opener` alive, **inherits the opener's webPreferences verbatim** — the same session partition, cookies and localStorage — and is closed automatically when it returns to the origin that opened it. `window.open()` never comes back `null` (a refused popup is rebuilt as a real linked window), the popup sends a **plain Chrome user-agent** rather than an Electron one, and the result travels back over `window.opener.postMessage` before the popup closes itself. Everything else keeps the old *"open in a new tab"* behaviour. Recognition and the UA live in the pure `oauth.js` module (unit-tested), the router in `main.js`.
- **Data at rest — encrypted database** *(new)* — the sensitive fields of `ghostview.db` are encrypted with **AES-256-GCM** (whole-file SQLCipher was rejected: field-level encryption keeps the rest of the schema queryable while the identifiers stay ciphertext). **Envelope model**: a random 32-byte data key (DEK) encrypts every field, and a key-encryption key derived from your login password — **PBKDF2-SHA512, 300,000 iterations, per-user random salt** — wraps only that DEK, stored in `user_keystores`. Every value is `AEG1:` + base64(IV‖tag‖ciphertext) and is authenticated against `AEG1|table|column|user_pseudo|scope`, so a value moved into another column, workspace or account **fails to decrypt instead of silently reading**. **Encrypted**: history, bookmarks and tabs (`url`, `title`), notes (`content`), page visits (`url`, `domain`, `title`), downloads (`filename`, `url`, `save_path`) and workspaces (`name`, `google_email`, `active_url`). **Plaintext by design**: `page_visits.category` — one coarse label the analytics `GROUP BY` needs — and every numeric, timestamp and aggregate column. An account that predates the vault is swept **once, on first login**, inside a transaction, followed by a **mandatory `VACUUM`** (with `secure_delete=ON` and a WAL checkpoint) so the old plaintext bytes are *rewritten out of the file* rather than merely overwritten; an interrupted sweep leaves `migrated=0` and simply runs again next login. **Changing your password re-wraps the same DEK** inside the change-password transaction — not a row of ciphertext is touched, so there is never a state where half the database wants the old password. The **duress password and guest mode derive no key at all** (a decoy that must look empty has nothing worth encrypting), and **no write ever falls back to plaintext**: if a navigation commits during quit teardown after the key was dropped, that write is discarded rather than stored unencrypted. Unlocking costs exactly one extra KDF (the third of the attempt); a damaged keystore reports a vault error **without spending a login attempt**.
- **Clipboard Auto-Wipe** *(new)* — text you copy inside AEGIS (right-click **Copy**, a page selection, plain **Ctrl+C**) is **cleared from the clipboard after a delay**: **on by default, 20 seconds**, adjustable from **5 to 600 seconds** in **Settings → Clipboard Auto-Wipe**. The wipe fires only when the clipboard still holds **exactly** the text that was copied — every copy (from AEGIS's own copy sites or from any other application, noticed by a 1.5 s poll) re-arms the timer, so something you copied afterwards is **never** cleared by an older timer. Whatever was on the clipboard **when AEGIS started is a baseline**: it is watched but never armed, so it is never wiped — and quitting clears the session's copy only when it differs from that baseline. *Known limitation:* **Windows' clipboard history (Win+V)** keeps its own copy of every entry; that list belongs to the operating system, is outside any application's reach and is **not** cleared by AEGIS — turn it off in Windows settings if copied text must not be remembered there.

## Requirements

Nothing on the target PC — both release formats bundle Node.js + Electron inside a single `.exe`.

## Building

```bash
npm install
npm start          # run from source
npm run release    # build AEGIS-Setup-<version>.exe + AEGIS-Portable-<version>.exe into dist\
```

Or double-click `Build Installer.bat`. Copy **either** single `.exe` to any Windows PC — do not copy the source folder or `node_modules`.

## Portable mode

AEGIS is portable-aware. It stores all user data (database, sessions, cookies) in a `data/` folder next to the app when:

- a `portable.dat` marker file sits next to the executable, or
- the `PORTABLE=1` environment variable is set, or
- a `data/` folder already exists next to the app.

Otherwise it uses the standard per-user `%APPDATA%` location.

## Settings

- **Profile** — photo, password change, **Duress password** (set or remove the second password that opens the decoy account; the card is always visible and reports when one is set).
- **Default Browser** — shows live status (green when AEGIS owns `http`/`https`), one-button registration, opens Windows Settings to confirm. *Windows 10/11 protect the default-browser choice, so the final "Set default" click happens in Windows Settings — AEGIS takes you straight there.*
- **Network Speed** — **Secure DNS** toggle (DNS-over-HTTPS, default OFF, applied at next launch, persisted to `net-prefs.json` in the profile folder). Parallel downloading is always on.
- **Browsing History** — password-gated history viewer.
- **Take Notes** — password-gated like History: enter your password once per opening, then write, edit and delete notes. Notes are **workspace-isolated** — each workspace has its own independent list (existing notes from older versions are migrated to the default workspace), and the header shows which workspace's notes you are seeing.
- **Idle auto-close** — enable/disable and set the timeout (in **AEGIS Parameters**, together with the default **Download folder** for all downloads).
- **Aegis Shield** — three switches: **Block ads & trackers**, **Fingerprint randomizer**, **Strip tracking parameters**. Each shows a live message when toggled, and the card shows the current counters (rules loaded, requests blocked, URLs stripped). Saved immediately to `shield-prefs.json` in the profile folder; add your own block rules to `shield-custom.txt` next to it.
- **Clipboard Auto-Wipe** — one switch plus the delay (**5–600 s**, default **on / 20 s**), saved immediately to `clipboard-prefs.json` in the profile folder. The card explains the exact-copy rule (only text that is still exactly what was copied is cleared; a newer copy is never touched by an older timer) and carries the **Win+V** caveat: Windows' own clipboard history is the OS's store, outside any application's reach, and is not cleared by AEGIS.

## Development

- `main.js` — main process: windows, `WebContentsView` tab management, SQLite persistence, IPC, OS integration.
- `preload.js` — `contextBridge` (exposed as `window.ghost`) — the only renderer→main surface.
- `shield.js` — the **Aegis Shield** engine (main process): rule parser + domain trie, the single `session.webRequest.onBeforeRequest` decision, the tracking-parameter strip, prefs/stats and the per-run fingerprint seed. It deliberately **never requires Electron** — `main.js` passes the profile folder to `init()` — which is what lets `node test-shield.js` drive it with plain node.
- `fp-preload.js` — the fingerprint-randomizer preload attached to every content view by `contentWebPreferences()` in `main.js` (`sandbox: true`, `contextIsolation: false` so the patches land in the page's own JS world). One IIFE, exposes nothing to the page, and asks the main process for its seed over `ipcRenderer.sendSync('shield-fp-bootstrap')`.
- `shield-list.txt` — the bundled block list (a **real EasyList + EasyPrivacy dump** with its licence headers and a syntax header; the current bundle parses to 99,264 loaded rules), shipped in `build.files` so the packaged build never falls back to the five-domain `BUILTIN_FALLBACK`.
- `playlist-queue.js` — the sequential queue behind **Download Full Playlist** (main process): the single-worker state machine that guarantees **one video at a time** (enqueue validation / dedupe / playlist order, pause / resume / cancel / skip / remove / retry, throttled progress + snapshots). Deliberately **Electron-free** like `shield.js` — `main.js` only injects the real yt-dlp runner — which is what lets `node test-playlist-queue.js` drive it with a fake one.
- `vault.js` — the **at-rest encryption** engine (pure crypto: no Electron, no filesystem, no database). Envelope key math only — PBKDF2-SHA512 (300 k) wrapping, AES-256-GCM field encryption with AAD binding (`AEG1|table|column|user_pseudo|scope`), the `AEG1:` plaintext/ciphertext marker, re-wrap on password change and DEK zeroization. `main.js` owns every storage decision (the table/column matrix, the first-login sweep + `VACUUM`, and all read/write call sites) — which is what lets `node test-vault.js` exercise the module with plain node.
- `oauth.js` — **SSO popup recognition** for the linked-popup router (pure module, no Electron/DOM): which `window.open()` targets are identity providers (host list + `/oauth…`/`/authorize` path rules on any host) versus ordinary tabs, plus the standard Chrome user-agent string the popup sends instead of Electron's.
- `login.html`, `workspace.html`, `controls.html`, `dashboard.html`, `settings.html`, `parameters.html`, `playlist.html`, `confirm-quit.html` — renderer pages (`playlist.html` is the frameless Download Full Playlist window: selection interface + active queue view).
- `audit.js` — static consistency check (JS/inline-script syntax, bridge-method coverage, IPC channel symmetry). Run with `node audit.js` before releasing.
- `test-geolocation.js` — E2E test for the silent geolocation refusal (`node test-geolocation.js`). Same isolated-sandbox harness: proves `navigator.permissions` reports geolocation as `denied` in **both** the default session and a real workspace tab, that `getCurrentPosition` fails with `PERMISSION_DENIED` in ~1 ms instead of hanging, and that the AEGIS process owns **no native dialog** during the request — a detector that is itself validated first against a real MessageBox titled "Permission Request" in a throwaway child process (including the PID filter), so a false "no popup" is impossible. It also asserts the page is visible first (Chromium never issues the request from a hidden page) and that every other permission still reports `granted`.
- `test-permissions.js` — E2E test for the silent approval of `persistent-storage` and `clipboard-sanitized-write` (`node test-permissions.js`). Same isolated-sandbox harness: proves both permissions are granted **with no dialog at all** (milliseconds, measured) in the default session, in a real workspace tab, in a second tab, in a **brand-new workspace created and switched to through the real bridge**, on a **real third-party HTTPS website** (`https://example.com`) and after a restart, while **camera still raises the native Allow/Deny dialog** — that dialog is answered with its own **Deny** button (never `WM_CLOSE`, which resolves as Allow in this Electron version), and its body is read through UI Automation inside **one PowerShell process started before the camera request** (so the dialog lives ~300 ms instead of a multi-second gap) to prove the popup names the exact permission string (`media`). The window/dialog detector is itself validated first against a real MessageBox titled "Permission Request" (including the PID filter), so a false "no popup" is impossible. Run with `node test-permissions.js`.
- `test-notes.js` — end-to-end test of the workspace-isolated, password-gated Notes (`node test-notes.js`). Same isolated-sandbox harness as `test-wipe.js`: it seeds a **legacy** `notes` table (no `workspace_id`) with an Electron-run helper to prove the migration backfills old notes to the default workspace, then asserts per-workspace scoping on the backend, the password gate in the real `controls.html` (including re-locking on reopen and Cancel closing the panel), that switching workspaces re-scopes the open list, and that deleting a workspace takes only its own notes.
- `test-wipe.js` — E2E test for the login self-destruct (36 checks). Copies the app into a temp sandbox with portable mode, drives the real login page over CDP through 4 phases (counter survives a restart → wipe → leftovers erased on the next launch → app reusable), and proves the project `data\` folder is never touched. Run with `node test-wipe.js`.
- `test-shield.js` — unit suite for the Aegis Shield engine (`node test-shield.js`): bundled + custom list loading, blocking with path and label boundaries, `$third-party` / resource-type / `$domain=` modifiers and `@@` exceptions, `handleRequest` (cancel vs redirect vs continue, loop guard, stats), `stripTrackingParams`, prefs persistence and the per-run seed. No Electron involved.
- `test-shield-e2e.js` — E2E test for Aegis Shield in the **launched app** (`node test-shield-e2e.js`). Same isolated-sandbox harness as the other E2E tests (copies `shield.js`, `shield-list.txt` and `fp-preload.js` in too): proves a `?utm_source=…&fbclid=…` navigation lands on the **cleaned** URL, that a tracker request fails with **`net::ERR_BLOCKED_BY_CLIENT`** — the error code only an interception produces, never a DNS or TLS failure — while a same-origin control resource still loads, that a solid canvas comes back with sparse noise while a **second origin farbles differently** and WebGL `readPixels` is noised too, and that all three Settings switches really turn their protection **off and back on**. It needs no internet: blocked hosts are intercepted before DNS runs, and the one probe deliberately left unblocked uses the reserved `.test` TLD.
- `test-ghost-duress-e2e.js` — E2E test for the **Ghost Workspace** and the **Duress Password** in the launched app (`node test-ghost-duress-e2e.js`, 91 checks). Same isolated-sandbox harness as the other E2E tests: proves the ghost card renders first with its "in-memory only" pill and no rename/delete buttons, that the ghost session starts with **empty cookie/localStorage on the same origin** the real workspace keeps storage on (separate partition), that leaving and reopening it starts a brand-new empty session, and that **nothing reaches the disk** — no `ghost-ephemeral*` path anywhere under `data\` and zero ghost-keyed rows in the SQLite file (read back with an Electron-run `better-sqlite3` helper after shutdown). For the duress password it proves the decoy account is believable but empty, the typed pseudonym is shown, every credential prompt inside it answers with the ordinary error, the real account's history/workspaces/duress setting survive untouched, and login timing with vs. without a duress password stays in the same range. It needs no internet: all probe pages come from a local `127.0.0.1` server.
- `test-playlist-queue.js` — unit suite for the sequential playlist queue (`node test-playlist-queue.js`, 106 checks, no Electron / no network): a fake runner counts concurrent starts and proves the **concurrency limit of 1**, strict playlist order (the next video starts only after the previous one reached a terminal state), failure isolation (a failed or throwing runner never blocks the queue), pause / resume / cancel / skip / remove / retry semantics (pause never starts anything new, a canceled queue can never be resurrected, remove only works before a video starts), progress throttling, snapshot emission on every state change and a 50-video strictly sequential run.
- `test-playlist-e2e.js` — E2E test for the whole **Download Full Playlist** feature in the launched app (`node test-playlist-e2e.js`, needs internet; `AEGIS_YT_PLAYLIST` overrides the playlist). Same isolated-sandbox harness as `test-youtube.js`: proves the button matrix (hidden off YouTube, on video pages and on `watch?v=…&list=…`; labelled exactly **"Download Full Playlist"** only on a complete playlist page, mutually exclusive with the single-video button), that pressing it opens the dedicated window and the listing streams in with thumbnails, durations, availability badges, preselected checkboxes and working select-all / deselect-all / filter counts, then — with the 3 shortest videos at 360p — that the queue downloads **one video at a time** (concurrency sampled from both the live state and the DOM: never more than one downloading row), that **Pause** lets the current video finish and starts nothing new, that **Resume** continues with the next video in playlist order, that **closing the playlist window does not stop the queue** (reopening it shows the running queue again), that every video completes as a real MP4 in the sandbox folder **in completion order** at the chosen quality and appears in the regular Downloads panel, plus: a second queue is refused while one runs, a new selection can **remove a waiting video** and **cancel** the queue (canceled counts correct, no partial-file debris, nothing ever starts afterwards) and the same safety guards as the other E2E tests (real `data\` snapshot byte-identical, real Downloads folder untouched).
- `test-oauth.js` — unit suite for `oauth.js` (`node test-oauth.js`, no Electron): which URLs are recognised as identity-provider popups (Google incl. country variants, Apple, Microsoft, OpenAI, Discord, Yahoo, Auth0, Okta, Amazon Cognito, generic `/oauth…` and `/authorize` endpoints on any host), which are ordinary tabs (search results, `accounts.google.com` reached as a top-level page, non-OAuth paths), blank-popup handling and the exact Chrome user-agent string.
